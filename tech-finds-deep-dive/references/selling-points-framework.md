# 4 维卖点提取框架

> skill 步骤 3 必须产出 4 维全有的卖点清单,**缺一不可**,缺了回到步骤 3 重提。
> 这是"用心"和"敷衍"的分水岭——市面同类 skill 通常只做第一维(功能卖点),后面三维全跳过。

---

## 维度 1:≥6 个差异化卖点

### 怎么提取
从 `scripts/read_project.py` 产出的项目摘要里挖。**不是功能列表**,是"差异化的、能戳到人的"卖点。

### 提取角度(从这 6 类各挖至少 1 个)
1. **架构亮点**:微服务?插件化?事件驱动?分层清晰?
2. **技术栈选型**:为什么用 React 不用 Vue?为什么 FastAPI 不用 Flask?有什么 trade-off?
3. **性能/工程化**:启动时间?包大小?CI/CD?有没有性能优化?
4. **解决的问题**:解决了什么真实痛点?别人是怎么解决的?为什么这个更好?
5. **代码质量**:有没有架构文档?测试覆盖率?类型注解?
6. **生态/可扩展**:能不能加插件?能不能二次开发?文档全不全?

### 达标标准(避免空话)
- ❌ 空话示例:"性能好"、"代码质量高"、"架构清晰"、"易于使用"
- ✅ 达标示例:"启动时间 200ms,比同类 YY 快 3 倍"、"用 LangGraph 实现状态机,比 if-else 链路清晰"、"CI 跑 3 个 job,2 分钟出结果"

### 验证问题(自检)
- 这个卖点换成竞品 YY 还成立吗?成立 → 不是差异化,重提
- 这个卖点有具体数字/技术细节吗?没有 → 太空,重提

## 维度 2:≥3 种典型用户画像的痛点场景

### 怎么提取
不是抽象的"用户痛",是具体的"场景 + 行为 + 痛点"。

### 3 个画像场景模板
每个画像必须给出:
- **画像**:谁(具体到身份/阶段)
- **场景**:他做什么的时候遇到这个问题
- **行为**:他现在怎么解决(笨办法)
- **痛点**:笨办法哪里痛
- **项目怎么救**:这个项目怎么帮他解决

### 示例(以一个 RAG 项目为例)
1. **画像**:大三计算机学生,准备秋招
   - **场景**:课设要做知识库问答系统
   - **行为**:自己从 Embedding 开始写,调通要 2 周
   - **痛点**:面试被问"RAG 怎么做的"答不出,因为没沉淀
   - **项目怎么救**:这个项目把 RAG 全流程封装,跟着做 1 天能跑通,且能讲清楚每步

2. **画像**:转码人,30+,做后端开发
   - **场景**:业务要做企业知识库
   - **行为**:用 LangChain 但文档散,踩坑多
   - **痛点**:出了 bug 不知道哪一层的问题
   - **项目怎么救**:这个项目用 LangGraph 把状态机画清楚,调试能看见每步

3. **画像**:技术博主,做 RAG 测评内容
   - **场景**:要做一期"RAG 项目对比"内容
   - **行为**:GitHub 找了 N 个项目,挨个跑
   - **痛点**:每个项目结构不一样,对比维度难统一
   - **项目怎么救**:这个项目结构清晰、文档全,可以当"基准线"对比其他项目

### 验证问题
- 这 3 个画像跟产品品类匹配吗?(教学项目不该有"资深架构师"画像)
- 每个画像的"项目怎么救"具体到项目特性吗?笼统 → 重提

## 维度 3:≥2 个最接近竞品并说清差异

### 怎么提取
找最接近的 2 个竞品(不是任意 2 个),说清"为什么选这个不选那个"。

### 提取步骤
1. 从项目 README/package.json/技术栈里识别项目类别
2. 找 2 个最接近的竞品:
   - 同品类(都是 RAG / 都是脚手架 / 都是 ORM)
   - 同语言生态(都是 Python / 都是 TS)
   - 同目标用户(都是学生党 / 都是开发者)
3. 对每个竞品说清:
   - **共同点**:都能解决什么
   - **差异点**:本项目强在哪、弱在哪
   - **trade-off**:什么场景选本项目、什么场景选竞品

### 示例
- 竞品 A(官方实现):本项目 fork 自 A,加了 X 模块、改了 Y 性能。**选本项目的理由**:开箱即用、有 X 模块;**选 A 的理由**:更稳定、社区更大
- 竞品 B(同类项目):B 用 LangChain,本项目用 LangGraph。**选本项目的理由**:状态机清晰、调试友好;**选 B 的理由**:生态成熟、文档全

### 验证问题
- 这 2 个竞品是"最接近"的吗?任意找的 → 重提
- 差异点有具体技术依据吗?笼统说"更好用" → 重提
- 有 trade-off 吗?只说本项目好不说弱项 → 不客观,重提

## 维度 4:≥1 个反直觉卖点(差异化护城河)

### 怎么提取
反直觉卖点 = "别人不写但能戳到人的点"。**这是这个 skill 区别于市面同类 skill 的核心护城河**。

### 反直觉卖点的 5 种来源
1. **设计反直觉**:看起来奇怪但实际巧妙的设计(如:为什么用 CSV 不用 JSON / 为什么不用 ORM)
2. **数据反直觉**:实测数据跟大众认知相反(如:大家都说 A 快,实测 B 快 3 倍)
3. **场景反直觉**:这个项目解决的不是你以为的问题(如:你以为它是 RAG 项目,实际它的核心是 prompt 管理)
4. **取舍反直觉**:放弃了一个看似重要的功能,反而更好(如:不支持多租户,反而简化了部署)
5. **学习路径反直觉**:大家都从 A 学起,但实际从 B 学起更快

### 提取方法
- 读架构文档/源码注释,找作者写的"为什么这么设计"
- 跑一遍项目,记下"咦,这里怎么是 X 不是 Y"的点
- 对比竞品,找本项目独有的、对手没有的"非主流"决策

### 示例
- "大家都以为这个项目的核心是 RAG,实际看源码会发现核心是 prompt 模板管理——这反而是它比竞品 YY 强的地方"
- "看似不支持多租户是缺点,实际跑一遍才懂:这反而是它部署简单的关键,适合个人/小团队"
- "实测发现它启动比同 star 数的竞品快 3 倍,原因是它没引入 ORM,直接 SQL——这是反直觉的设计取舍"

### 验证问题
- 这个卖点是不是"看了 README 第一段就知道"的?是 → 太浅,重提
- 这个卖点能不能让读者"哦?原来如此"一下?不能 → 不够反直觉,重提
